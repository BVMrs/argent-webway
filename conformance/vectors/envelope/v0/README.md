# `envelope/v0` test vectors

Language-neutral vectors for [`spec/ext/envelope.md`](../../../../spec/ext/envelope.md). Do not edit these files
by hand. They are generated by [`conformance/tools/envelope-vectors`](../../../tools/envelope-vectors), which checks
every case against a reference verifier while it builds it:

```sh
cd conformance/tools/envelope-vectors
cargo run -- generate   # rewrite the files
cargo test              # fails if the files are stale or the spec's Appendix A and the vectors disagree
```

## Common shape

Every file except `keys.json` has the same top-level shape:

```json
{
  "spec": "spec/ext/envelope.md",
  "version": "webway-envelope/0",
  "kind": "envelope-verify",
  "description": "…",
  "generator": "conformance/tools/envelope-vectors",
  "constants": { "SKEW_SECONDS": 300, "MAX_TTL_SECONDS": 604800, "MAX_ENVELOPE_BYTES": 1048576, "MAX_DEPTH": 64 },
  "cases": [ { "id": "…", "requirements": ["ENV-…"], "description": "…", …, "expect": { … } } ]
}
```

- `id` is stable. `requirements` lists the spec IDs the case tests. A harness reports results per requirement.
- `input` is the exact JSON text the implementation under test receives, given as a JSON string. Re-serialising
  it would defeat cases that test whitespace, member order, escapes, number spellings and duplicate keys.
  `input_hex` replaces `input` when the bytes are not valid UTF-8.
- An expected error is `{"type", "code", "reason", "retryable"}`, plus `retryAfter` (seconds) for
  `EnvelopeNotYetValid`. The type, reason and retryable flag must match exactly (ENV-610). The codes are
  provisional (spec §10.1).
- Every invalid case has **exactly one defect**, so the expected error does not depend on the order in which an
  implementation runs the stateless checks (ENV-601). In particular, whenever `from` and `sig` can be decoded at
  all, the signature over the (possibly defective) signed header is **valid**. Edited headers are re-signed, and a
  non-canonical spelling of alice's key (`from-uppercase`, `from-non-canonical-base32`) is signed by alice, so a
  lax decoder would accept it. The only cases with an invalid signature are those that expect `SignatureInvalid`,
  and `version-unsupported`, which is never verified under v0 rules (ENV-800). The generator asserts this rule for
  every case.

## Files

| File | `kind` | What the implementation does with each case |
|---|---|---|
| `keys.json` | n/a | Test key pairs (seeds, public keys, `wwa:` IDs, `did:key`s). **Test keys only.** |
| `jcs.json` | `jcs` | Parse `input` as I-JSON (§4.1) and canonicalise with RFC 8785 (§4.2). Expect `{"result": "canonical", "canonical": "…"}` (compare the UTF-8 bytes) or a rejection. |
| `envelopes.json` | `envelope-verify` | Run verification steps 1–7 (§9) as a node that hosts `receiver.hosts`, with clock `receiver.now`, optional purge watermark `receiver.watermark`, optional `receiver.framing_op` (the operation named by unsigned framing) and optional `receiver.extension_ops` (the extension operations it implements, none if absent; it always implements the A2A operations, ENV-022). Accepted cases also give `from`, `id`, `body_hash`, `signed_header_jcs`, `signing_input_hex` and `header_digest`, for debugging. |
| `header-only.json` | `header-signature` | `input` is a stored signed header with the body removed (ENV-213). Verify the signature only. |
| `freshness.json` | `freshness` | Pure function of `now`, `ts`, `exp` and an optional `watermark` (§6, ENV-504). |
| `replay.json` | `replay` | Stateful scenarios, below. |

### `replay.json` scenarios

Each scenario starts a fresh receiving node that hosts `receiver.hosts` with an empty dedupe store and purge
watermark `receiver.initial_watermark`. `envelopes` maps names to envelope texts. Run `steps` in order:

| `action` | Meaning |
|---|---|
| `receive` | Deliver `envelopes[envelope]` at time `now`. `transport` is `authenticated` (the binding authenticated the peer as the sender's node or the receiver's mailbox host) or `unauthenticated`. `app_result`, if present, is what processing returns: `retryable-error` or `fatal-error` (default: success). |
| `sent` | The node itself sent `envelopes[envelope]`. Answers to it are now solicited (ENV-401). |
| `purge` | Remove dedupe entries with `exp + SKEW < now` and raise the watermark (ENV-502, ENV-504). |

Expected outcomes of `receive`:

| `outcome` | Meaning |
|---|---|
| `process` | New request, processed. `dedupe_entry` says whether an entry must now exist (ENV-501, ENV-521). |
| `duplicate` | Not processed. `answer` is `stored` (the stored envelope, byte for byte, ENV-530) or `ack` (the duplicate ack, ENV-531). |
| `deliver` | A solicited answer, delivered to the local agent. |
| `drop-duplicate` | A duplicate answer, dropped without a reply (ENV-512). |
| `discard` | An answer discarded without a reply (ENV-402). `reason` is `unsolicited` (ENV-401) or `unsupported-op` (ENV-022). |
| `reject` | Rejected with `error`. |

## What the vectors do not cover

Some requirements need time, crashes, transports or several nodes: durable atomic dedupe entries (ENV-503),
concurrent duplicates (ENV-505), signed versus unsigned errors (ENV-620–622), intermediary behaviour
(ENV-700–702), the size limit (ENV-101). The black-box harness (T4) tests those. The spec's Appendix A says,
for each requirement, which vector file or harness test covers it.

The body schema checks (signer form, Appendix B locations) follow `a2a.proto` at tag `v1.0.1`. The capability
values in `cap` are placeholders, not Biscuit tokens: the envelope layer treats them as opaque.
